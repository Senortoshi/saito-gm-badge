## Key Question 1: Does Saito have native, protocol-level NFT support?

### Takeaway
Yes. Saito has consensus-level NFT support implemented as a new slip type (`SlipType::Bound`) and transaction type (`TransactionType::Bound`), designed in Saito Implementation Proposal 003 ("Bound UTXO", Feb 2025), first merged into the Rust core in November 2024, hardened through 2025, and shipped with the December 2025 mainnet launch (marketed as "Smart NFTs"). There is no VM or smart contract; an NFT is a consensus-recognized arrangement of three UTXO slips.

### Cited Findings
- SIP-003 "Bound UTXO" (author David Lancashire, created February 20, 2025, status Published) states: "This proposal provides an alternate way to publish and trade NFTs on Saito without the need for a supporting VM." It introduces "a new type of transaction slip (UTXO) that we refer to as a BoundUTXO" with the same data structure as other slips but repurposed fields: `type - BoundUTXO`, `amount - the amount of tokens/assets`, `address - the unique ID of the NFT/asset`. — [SIP-003 Bound UTXO](https://github.com/SaitoTech/saito-implementation-proposals/blob/master/proposals/003_bound_utxo.md)
- Commit history in `saito-rust-workspace`: 2024-09-11 "Added new slip type and transaction type for supporting NFTs"; 2024-09-16 "Added some checks for NFT support"; 2024-11-08 merge of PR #815 "NFT Support" (feature/814/nft branch); 2025-04-10 through 2025-05-09: "wallet.rs NFT feedback", "Check for nft_input_amount == nft_create_deposit_amt in create_bound", "nft transaction validation", "Helper method for nft_uuid", "add nft_type", "Update ATR logic to handle nft group slips", "Generic method for identifying if tx is_nft". — [GitHub commit search, saito-rust-workspace](https://github.com/SaitoTech/saito-rust-workspace/commits/master); [PR #815 NFT Support](https://github.com/SaitoTech/saito-rust-workspace/pull/815)
- The Saito blog "Saito Summer 12 - The Big Picture" (published November 4, 2024) described an NFT as "a special UTXO that is bound to another UTXO that has fees and can be transferred normally," called it "a flexible and simple NFT standard for Saito Mainnet," said NFTs are "lighter and cheaper to create and send," said "Split NFTs" would define a fungible token standard, and stated "The standard is under development and currently under testing." — [Saito Summer 12 (archive.saito.io)](https://archive.saito.io/saito.tech/saito-summer-12-the-big-picture/)
- The consensus NFT module `rust/saito-core/src/core/consensus/nft.rs` defines `pub struct NFTTuple { slip1, slip2, slip3 }` with the comment "Bound (slip1) – Normal|ATR (slip2) – Bound (slip3); slip3.amount == 0." and `from_slips` rejects anything else: `if slip1.slip_type != SlipType::Bound || slip3.slip_type != SlipType::Bound || !(slip2.slip_type == SlipType::Normal || slip2.slip_type == SlipType::ATR) { return None; } if slip1.amount == 0 || slip3.amount != 0 { return None; }`. — [nft.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/nft.rs)
- `Transaction::is_nft(&self, slips, i)` in `rust/saito-core/src/core/consensus/transaction.rs` (line ~1752) returns true only when `slips[i]` is Bound, `slips[i+2]` is Bound, and `slips[i+1]` is Normal or ATR. — [transaction.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/transaction.rs)
- Saito's December 16, 2025 mainnet press release (GlobeNewswire, Hong Kong dateline) lists "Smart NFTs: dynamic, logic-bearing assets that eliminate the need for complex virtual machines" as a key mainnet feature. — [Manila Times / GlobeNewswire press release](https://www.manilatimes.net/2025/12/16/tmt-newswire/globenewswire/saito-blockchain-launches-mainnet-pioneering-decentralised-web3-infrastructure/2244176)
- The wiki roadmap page (dated 2025-11-11) says: "With token persistence a reality and ATR payouts scaling with total network fee-throughput, core development is now focused on advanced features like NFT support, a simplified scripting language for multi-sig support..." — [wiki roadmap.md](https://github.com/SaitoTech/wiki/blob/master/roadmap.md)
- The "Refactor 2026 – Rust Pipeline" wiki page (dated 2026-07-19) lists under "Digital Asset Infrastructure": "Native token implementation; Native NFT implementation; NFT split support; NFT merge support; New slip types supporting programmable ownership." — [wiki refactor-2026/rust-pipeline.md](https://github.com/SaitoTech/wiki/blob/master/refactor-2026/rust-pipeline.md)
- A SaitoOfficial X post (approx. early September 2025, "Core Node Update Summary") mentioned that malformed NFT slips are now rejected earlier in validation and fixes to NFT group validation (per search snippet; the full post could not be fetched directly — HTTP 402). — [X post 1963024866422161889](https://x.com/SaitoOfficial/status/1963024866422161889)

### Inferences
- NFT support is a hard consensus feature (slip type + transaction type + ATR rules + opcodes), not an application-layer convention. Applications cannot "fake" an NFT: the tuple shape is validated in Rust.
- The design is deliberately contract-free and UTXO-native, in keeping with Saito's anti-VM positioning; "Smart NFT" in marketing means an NFT whose transaction payload can carry JS/CSS/app bundles that the wallet executes locally, plus optional P2SH scripts, not an on-chain VM.

### Gaps
- I could not retrieve the full text of the Sept 2025 X "Core Node Update" post (paywalled fetch), so the exact wording on NFT slip validation is from a search snippet only.
- No formal "Saito NFT standard" document numbered like an ERC exists beyond SIP-003 and the internal README chapter; the team explicitly says not to add "a metadata URI standard."

## Key Question 2: How are NFTs represented? How are uniqueness and ownership enforced? Can an NFT be transferred, split, or burned?

### Takeaway
An NFT is exactly three consecutive slips in a `Bound` transaction: slip1 (Bound, amount = quantity, pubkey = creator), slip2 (Normal/ATR, amount = SAITO deposit, pubkey = current owner), slip3 (Bound, amount = 0, pubkey = 33-byte NFT id). The id is derived from the UTXO coordinates spent at mint, guaranteeing uniqueness; ownership is whoever can sign for slip2. NFTs support transfer, quantity (so they double as fungible tokens), split, merge, atomize, and removal ("burn"), plus P2SH-locked ownership.

### Cited Findings
- Tuple layout per the internal developer README: "slip1 | Bound | quantity, must be greater than 0 | creator; slip2 | Normal or ATR | deposit in nolans, may be 0 | current owner; slip3 | Bound | must be 0 | NFT id." "slip1's amount is a quantity of this NFT, not a SAITO balance... slip2 is the spendable custody slip. Moving the NFT means spending slip2 together with the two bound slips... slip3 carries the id. Its amount is always 0. Its 33-byte public key is not a user key." — [SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Uniqueness: `Wallet::create_nft_uuid(input_slip, nft_type) -> [u8; 33]` in `wallet.rs` concatenates `block_id` (8 bytes BE) + `tx_ordinal` (8 bytes BE) + `slip_index` (1 byte) = "a 17-byte 'fingerprint' that no one else can duplicate unless they somehow create an identical UTXO," then embeds `nft_type` as UTF-8 in the remaining 16 bytes (zero-padded or truncated). — [wallet.rs create_nft_uuid](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/wallet.rs)
- SIP-003 on uniqueness: "The id for a BoundUTXO is determined by the first UTXO that is spent in the transaction that creates it... This ensures uniqueness across the network -- not even the user who created the NFT can create a second one with the same ID as they will need to use a different UTXO to do so. As the NFT moves around, its own unique ID remains the same by consensus rules." — [SIP-003](https://github.com/SaitoTech/saito-implementation-proposals/blob/master/proposals/003_bound_utxo.md)
- Ownership enforcement per SIP-003: "transactions that move BoundUTXO must also move the UTXO which are immediately after them in the transaction... This provides a guarantee that only the NFT owner can move the NFT." — [SIP-003](https://github.com/SaitoTech/saito-implementation-proposals/blob/master/proposals/003_bound_utxo.md)
- Accessors in `nft.rs`: `get_id` = lowercase hex of slip3 pubkey; `get_type` = bytes 17..33 of slip3 pubkey with trailing zeros stripped; `get_creator` = slip1 pubkey base58; `get_owner` = slip2 pubkey base58; `get_amount` = slip1.amount; `get_deposit` = slip2.amount. `verify_owner_tx_signature(tx, owner_public_key)` checks the tx signature against slip2's key. — [nft.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/nft.rs)
- Mint: `Wallet::create_bound_transaction(nft_num, nft_create_deposit_amt, tx_msg, recipient, ..., nft_type)` sets `transaction.transaction_type = TransactionType::Bound`, generates input slips covering the deposit, errors "Failed to generate input slip for creating NFT" if none, and uses one input slip as the UUID source. Source comment: "all NFTs have a UUID that is created from the UTXO slip that the creator selects as an input value... no-one else will be able to create an NFT with the same values." — [wallet.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/wallet.rs)
- Rust wallet functions for the full lifecycle (line numbers in wallet.rs): `generate_nft_slips` (931), `create_nft_transaction` (1165, transfer by id/amount), `create_bound_transaction` (1405, mint), `create_send_bound_transaction` (1621, legacy single-triple send), `create_split_bound_transaction` (1698), `create_atomize_bound_transaction` (1793), `create_merge_bound_transaction` (1902), `create_remove_bound_transaction` (2052, burn/spend-out), `create_nft_uuid` (2133), `return_nft_sender_publickey` (2463), `add_nft` (2502). — [wallet.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/wallet.rs)
- Transfer semantics: "`create_nft_transaction` in `wallet.rs` spends existing triples for `nft.id`. It does not mint... Outputs are new Bound / Normal / Bound triples: creator preserved, recipient on slip2, the same slip3 id, quantity split across recipients, deposit split in proportion to quantity." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Quantity/fungibility: "Quantity is slip1's amount. It is an integer on the slip. It is not required to be 1. Vault mints `BigInt(1)`. A token-style NFT mints or transfers a larger `num`." Wallet ops: `createSplitNFTTransaction(nft, leftCount, rightCount)`, `createMergeNFTTransaction(nft)` ("same-id only"), `createAtomizeNFTTransaction(nft)` ("`NFTAtomize` caps the UI at 20 outputs per transaction, 100 total, and 5 transactions per block. Those caps are in the overlay, not in consensus."), `createRemoveNFTTransaction(nft)` ("Spend the triple out"). — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Commits: 2026-03-03 "handling split nfts" / "All selection of shard in NFT transfer"; 2026-03-04 "clean up handling of multiple NFT shards"; 2026-07-01 "nft token fixes". — [saito commit search "nft"](https://github.com/SaitoTech/saito/commits/master)
- Token-style wrapper: `node/lib/templates/nftcryptomodule.js` (`NFTCryptoModule.sendPayment`) "is the token-style wrapper: `createNFTTransaction` for a numeric amount, `modifyBeforeSend`, `sign`, `propagateTransaction`. It is how an NFT type behaves as a balance. It is not a second ledger." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md); [nftcryptomodule.js](https://github.com/SaitoTech/saito/blob/master/node/lib/templates/nftcryptomodule.js)
- On-chain ownership check by third parties: the RustScript opcode `CHECKOWNNFT` (`rust/saito-core/src/core/consensus/scripting/opcodes/checkownnft.rs`) takes `witness.utxokey1..3`, rebuilds the tuple via `tuple_from_utxo_hex_keys`, requires `blockchain.is_slip_unlocked(key1)` (and key2 if slip2.amount > 0), then `verify_owner_tx_signature(tx, &tuple.slip2.public_key)`. `CHECKOWNNFTWHERE` adds `creator`/`type` equality clauses. — [checkownnft.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/scripting/opcodes/checkownnft.rs); [wiki rustscript.md](https://github.com/SaitoTech/wiki/blob/master/rustscript.md)
- Programmable ownership (P2SH): "Refactor 2026 brings native P2SH support to Saito, allowing users to transfer SAITO and NFTs to addresses which impose restrictions on who can subsequently transfer, split, merge or destroy them." Lists "Multisignature ownership. Conditional ownership transfers. Time-locked ownership. Programmable royalty enforcement. Escrow-capable ownership." — [wiki refactor-2026/decentralized-finance.md](https://github.com/SaitoTech/wiki/blob/master/refactor-2026/decentralized-finance.md); [wiki refactor-2026/assets.md](https://github.com/SaitoTech/wiki/blob/master/refactor-2026/assets.md)
- The JS/WASM bridge: `rust/saito-wasm/src/wasm_nft.rs` exposes `WasmNFT` with getters/setters for `id`, `tx_sig`, `ticker`, `slip1`, `slip2`, `slip3`; `rust/saito-js/lib/nft.ts` wraps it as class `Nft` with `toJSON()` emitting id, tx_sig, ticker, and per-slip `amount, slip_type, public_key, block_id, tx_ordinal, slip_index, utxo_key`. — [wasm_nft.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-wasm/src/wasm_nft.rs); [nft.ts](https://github.com/SaitoTech/saito/blob/master/rust/saito-js/lib/nft.ts)

### Inferences
- Because quantity lives on slip1 and split/merge are native, the same primitive is simultaneously Saito's "NFT standard" and its "fungible token standard" (the wiki calls this "Expanded NFT types including cryptocurrency tokens"). An NFT with quantity 1 is non-fungible; quantity N is a colored-coin-style token.
- "Burning" is `create_remove_bound_transaction` (spending the triple out without re-creating it); SIP-003 also implies NFTs die if their paired UTXO is missing at rebroadcast.
- The `nft_type` string is a 16-byte on-chain label (e.g., `stack`, `vault-nft-key`, `saito-app`, `image`, `css`, `js`, `token`), which is how different apps interoperate on the same asset.

### Gaps
- I did not read the full bodies of `create_split_bound_transaction`, `create_merge_bound_transaction`, or `create_remove_bound_transaction` to confirm edge-case validation (e.g., whether consensus enforces that split outputs sum to input quantity; the README says consensus "moves slip1's amount").

## Key Question 3: How does Automatic Transaction Rebroadcasting (ATR) interact with NFTs? Do NFTs need a balance to stay alive? What is the "rent" model?

### Takeaway
Yes: an NFT survives ATR only via the SAITO deposit on its slip2 ("payload slip"). At each ATR cycle the node computes a fee from the rebroadcast transaction size times the previous block's average fee-per-byte; if the slip2 deposit times the ATR multiplier exceeds that fee, the triple is rebroadcast as a new `[Bound, ATR, Bound]` group with the fee deducted; otherwise the Bound slips are not rebroadcast and the NFT falls off the chain. All NFT groups in one transaction are merged into a single rebroadcast transaction.

### Cited Findings
- SIP-003 rules: "2. ATR rebroadcasting moves the BoundUTXO together with the UTXO immediately after it. 3. BoundUTXO that are missing their paired UTXO are removed from the chain on rebroadcasting." — [SIP-003](https://github.com/SaitoTech/saito-implementation-proposals/blob/master/proposals/003_bound_utxo.md)
- `block.rs` (lines ~1711–1920) collects `nft_groups: Vec<(Slip, Slip, Slip)>` by scanning for the `[Bound, Normal, Bound]` pattern (comment: "slip1 provides the NFT identifier... slip3 re-encodes the NFT UUID for provenance"), then: "Generate a single ATR rebroadcast transaction for all NFT groups so they move together as one UTXO in the network." It computes `let atr_fee = tx_size * previous_block_avg_fee_per_byte;`, `let atr_payout_for_slip = slip2.amount * expected_atr_multiplier;`, and `if atr_payout_for_slip > atr_fee { ... to_slip2.slip_type = SlipType::ATR; to_slip2.amount = atr_payout_for_slip - atr_fee_for_slip; ... Transaction::create_rebroadcast_bound_transaction(...) } else { // Payload slip didn't cover fee ... debug!("we don't rebroadcast Bound slip in tx - {:?} since atr_payout_for_slip = {:?} atr_fee = {:?}") }`. — [block.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/block.rs)
- Block validation elsewhere in `block.rs` skips Bound slips as fee-paying inputs: `if input.amount == 0 || input.slip_type == SlipType::Bound { ... }` (lines ~675, 1395, 3454), and rebroadcast validation checks "whether this is an NFT-group ATR (3 slips) or a single-slip ATR" by inspecting `rebroadcast_tx.from[0..3]` slip types (line ~2058). — [block.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/block.rs)
- README: "Its [slip2's] amount is the SAITO deposit that travels with the NFT and is what automatic transaction rebroadcast (ATR) treats as the payload." "Deposit on slip2 is independent: it is SAITO locked to the triple, and ATR pays on that deposit rather than on the quantity." "ATR may later rewrite the triple into a new transaction. `tx_sig` on the list entry then points at the rebroadcast, which is why `fetchTransaction` searches by id as well as signature." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Wallet bookkeeping: "`updateNFTList` groups by id. A change that only replaces slips is classified as `rebroadcast` (ATR moving the same NFT). A change in count or payload is `updated`." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Vault's mint example uses a one-SAITO deposit: "`createMintNFTTransaction(BigInt(1), oneSaitoDeposit, txmsg, 0, ownKey, nft_type)`." The `NFTOverlay` exposes `setDeposit / getDeposit` to "Convert between SAITO and the nolan deposit on the object." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Commit 2025-04-23 "Update ATR logic to handle nft group slips" (saito-rust-workspace). — [commit search](https://github.com/SaitoTech/saito-rust-workspace/commits/master)
- Saito's general ATR/persistence framing: "With token persistence a reality and ATR payouts scaling with total network fee-throughput..." — [wiki roadmap.md](https://github.com/SaitoTech/wiki/blob/master/roadmap.md)

### Inferences
- The "rent" model is identical to ordinary SAITO UTXO rent: the deposit pays a rebroadcast fee each genesis period, offset by the ATR payout multiplier. Because the fee is proportional to transaction size (`tx_size * avg_fee_per_byte`) and the NFT's message (`transaction.data`) is part of that transaction, NFTs with large embedded payloads (base64 images, JS bundles) cost more to keep alive per cycle than NFTs that reference external/Archive content.
- An NFT minted with zero deposit (allowed: "may be 0") will not survive its first ATR cycle unless topped up (the code path for `atr_payout_for_slip > atr_fee` fails when slip2.amount = 0).
- Merging all groups in a transaction into one rebroadcast reduces per-NFT overhead for batch mints.

### Gaps
- I did not find a user-facing doc stating recommended deposit sizes or the current genesis period length / ATR multiplier on mainnet; those values live in consensus constants not reviewed here.
- Whether a wallet can "top up" an existing NFT's deposit without a transfer is not documented in what I read (the README says `setDeposit` "does not rewrite a confirmed slip").

## Key Question 4: Where does NFT media/metadata live?

### Takeaway
Metadata and media are **not** in the UTXO slips. They live in the mint/transfer transaction's `data` field (`tx_msg`: title, description, image, css, js, text, saito bundle, file_id, path hops), which nodes/wallets retrieve from the local Archive or a peer. Large content is either embedded inline (base64 in the transaction) or referenced by id to a file stored in Saito's Archive service (e.g., Vault). There is no IPFS or metadata-URI standard; Saito explicitly rejects adding one.

### Cited Findings
- "A mint transaction's message is separate from the tuple. `create_bound_transaction` stores `tx_msg` in `transaction.data`. Title, image, file id, access script, and path hops live there. The UTXO set keeps the slips. It does not keep the message. After the transaction is confirmed, a wallet that owns slip2 can see the tuple. It still needs the transaction, usually from the local Archive, to read the message." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- `SaitoNFT.extractNFTData` copies `data.image`, `data.css`, `data.js`, `data.text`, `data.saito`, `txmsg.title`, `txmsg.description`, `data.expires_at`. Lookup order: local Archive by `{sig: tx_sig}` or `{field4: id}`, then "ask the first connected peer and, on success, `saveTransaction` locally with `{ field4: id, preserve: 1 }`." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- "Large content does not belong in the tuple. It may be inline in `data` when it is small enough to justify the transaction, or it may be a reference. Vault stores the file in Archive and puts `file_id` on the NFT message. Stack stores the post in Archive and uses the NFT only as the credential. Prefer a reference when the payload is a file, a ROM, or a module the user will fetch again." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- "A confirmed NFT with no Archive copy of its transaction will show in the wallet and fail to render. Handle `load_failed` on `SaitoNFT`. Do not treat a missing image as a missing NFT." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Explicit anti-standard guidance: "Represent an NFT as the three-slip tuple. Do not add an ERC-721 contract, token id counter, or metadata URI standard." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- The public wiki shows embedded-media NFTs: the "Replace Images with Embedded Images" recipe uses `const replacement_image = \`data:image/png;base64,iVBORw0KGgo...\`` and notes "This makes the NFT larger, but eliminates the need to fetch content from another server." The external-image recipe instead references `https://saito.io/saito/img/arcade/cards/purple_back.png`. — [wiki nfts.md](https://github.com/SaitoTech/wiki/blob/master/nfts.md)
- Store caches NFT images server-side: `expressapp.get(\`${uri}/cache/:nft_id.img\`, ...)` in `store.js` `webServer`, and `lib/images.js` exports `serveCachedImageResponse`. — [store.js](https://github.com/SaitoTech/saito/blob/master/node/mods/store/store.js)
- Vault access pattern: "Vault's default key is `CHECKOWNNFT` with those three witness keys. The file is an Archive row whose `owner` is the script hash. The NFT message holds `file_id` and `file_access_script`. The NFT is not the file." Download "is a peer request `vault access file` carrying the witnessed script." — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md); [vault.js](https://github.com/SaitoTech/saito/blob/master/node/mods/vault/vault.js)

### Inferences
- Persistence of media is coupled to the transaction's survival (ATR) for inline content, and to Archive node retention for referenced content; an NFT holder who was offline may hold a valid tuple but be unable to render it if no peer archived the mint transaction.
- There is no content-addressing: `file_id` is the file transaction's signature, not a hash of the bytes.

### Gaps
- I found no documentation of Archive retention guarantees / pricing for NFT-referenced files beyond the general Archive service.

## Key Question 5: What NFT apps, modules, galleries, or marketplaces exist on Saito? What can users do today?

### Takeaway

## Key Question 8: Code-level API summary (how it works, where it lives)

### Takeaway
Rust `saito-core` owns the primitive (slip/transaction types, tuple parsing, mint/transfer/split/merge/atomize/remove, ATR, `CHECKOWNNFT`); `saito-wasm`/`saito-js` expose `WasmNFT`/`Nft`; the Node/browser layer (`node/lib/saito/wallet.ts`) wraps them as `createMintNFTTransaction`, `createNFTTransaction`, etc., and `SaitoNFT` + `saito-nft/` UI render and manage them. Modules extend behavior via `respondTo('saito-create-nft')` and `respondTo('saito-nft-transfer')`.

### Cited Findings
- JS mint call: `app.wallet.createMintNFTTransaction(BigInt(quantity), depositNolan, txmsg, feeNolan, recipientPublicKey, nftType)` → `Wallet::create_bound_transaction`. — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- JS transfer: `await nft.fetchTransaction(); let tx = await app.wallet.createNFTTransaction(nft, recipientPublicKey, amount, fee, saitoDeposit, txmsg); tx = await nft.modifyBeforeSend(tx, recipientPublicKey, transferData); await tx.sign(); await app.network.propagateTransaction(tx);` — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Wallet API table: `wallet.getNFTList()`, `updateNFTList()` (returns `{ updated, rebroadcast, persisted }`), `addNft(slip1, slip2, slip3, id, txSig, ticker)`, `saveNFTList`, `loadNFTs()` ("Skipped when the URL contains `nonfts`"), `extractNFTType(hex)`, `computeNFTIdFromTx(tx)`, `createMintNFTTransaction`, `createNFTTransaction`, `createNFTShardTransaction` (legacy), `createSplitNFTTransaction`, `createMergeNFTTransaction`, `createAtomizeNFTTransaction`, `createRemoveNFTTransaction`. Holdings live in `app.options.wallet.nfts`; each entry has `id, slip1, slip2, slip3, tx_sig, ticker?`. — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- saito-js `Wallet` class (`rust/saito-js/lib/wallet.ts`) exposes `addNft(...)` (calls `this.instance.add_nft`) and `createNFTTransaction(..., nftAmount: bigint, nftUuid: string, ...)`. — [wallet.ts](https://github.com/SaitoTech/saito/blob/master/rust/saito-js/lib/wallet.ts)
- `SaitoNFT` domain object (`node/lib/saito/ui/saito-nft/saito-nft.js`): `new SaitoNFT(app, mod, tx, walletEntry)`; methods `fetchTransaction(callback, localhost_only)`, `returnType()`, `returnCreator()`, `returnMediaDisplay()/returnImage()`, `modifyBeforeSend(tx, receiver, data)`, `setDeposit/getDeposit`, `getSlipCount/getTotalAmount/returnAllSlips`, `remainingExpiresLabel()`. — [README NFTs chapter](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md); [saito-nft.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/saito-nft.js)
- Extension points: "Modules add mint types by returning an object from `respondTo('saito-create-nft')` with `title`, `class` (the type string passed as `nft_type`), `text`, and optional `createData`." "`modifyBeforeSend`... collects `respondTo('saito-nft-transfer')` handlers whose `class` array contains `returnType()`, and calls `onTransfer(nft, tx, receiver, data)`.

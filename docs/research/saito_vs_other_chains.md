## Key Question 1 — Storage model: where NFT media/metadata lives on each chain, and what Saito's ATR "pay rent or be pruned" model means versus permanent storage

### Takeaway
Saito is the only chain in this comparison where (a) the NFT is a *three-slip UTXO tuple* rather than a contract record, (b) the asset must be re-paid-for every epoch (~80,640 blocks, roughly 28 days at the default 30 s heartbeat) via Automatic Transaction Rebroadcasting (ATR), funded by a SAITO deposit locked inside the NFT, and (c) the media payload is explicitly *not* consensus state — it lives in the transaction message and is served by application-layer Archive nodes. Ethereum/Solana/Tezos/Polkadot keep a small on-chain record plus an off-chain pointer by default; Bitcoin Ordinals and BSV 1Sat put full bytes on-chain once, forever; Arweave sells a one-time 200-year endowment.

### Cited Findings

**Saito NFT primitive (as implemented, 2026)**
- Consensus recognizes an NFT as three consecutive slips in a `TransactionType::Bound` transaction: slip1 = `Bound`, amount = quantity (>0), key = creator; slip2 = `Normal` or `ATR`, amount = SAITO deposit in nolans (may be 0), key = current owner; slip3 = `Bound`, amount must be 0, key = NFT id. "slip2 is the spendable custody slip." "Bound slips that are not part of this triple are not an NFT." — [SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Rust core: `NFTTuple { slip1, slip2, slip3 }`; "Bound (slip1) – Normal|ATR (slip2) – Bound (slip3); slip3.amount == 0"; NFT id = lowercase hex of slip3's public key; the NFT *type* string is bytes 17..33 of that key (16-byte UTF-8, zero-padded) — [nft.rs](https://github.com/SaitoTech/saito/blob/master/rust/saito-core/src/core/consensus/nft.rs)
- The 33-byte NFT UUID layout: block ID (8 bytes big-endian), tx ordinal, slip index, then a 16-byte type string; derived from the UTXO spent at mint — [wallet.rs (saito-rust-workspace)](https://github.com/SaitoTech/saito-rust-workspace/blob/master/saito-core/src/core/consensus/wallet.rs)
- Slip type enum: Normal 0, ATR 1, VipInput 2, VipOutput 3, MinerInput 4, MinerOutput 5, RouterInput 6, RouterOutput 7, BlockStake 8, Bound 9, P2SH 10; transaction types include Bound 8 and ATR 3 — [SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md](https://github.com/SaitoTech/saito/blob/master/README/consensus/SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md)
- Older public framing (Nov 2024): "A Saito NFT is a special UTXO that is bound to another UTXO that has fees and can be transferred normally"; "NFTs are lighter and cheaper to create and send"; "'Split NFTs' are possible, defining a fungible token standard within the Bound-UTXO framework"; at that time "The standard is under development and currently under testing" — [Saito Summer 12 – The Big Picture (2024-11-04)](https://archive.saito.io/saito.tech/saito-summer-12-the-big-picture/)
- Mainnet was declared 16 Dec 2025; the press release lists "Smart NFTs: dynamic, logic-bearing assets that eliminate the need for complex virtual machines" and ATR as launch features (press release text via search summary; page itself returned HTTP 403) — [StreetInsider / GlobeNewswire](https://www.streetinsider.com/Globe+Newswire/Saito+Blockchain+Launches+Mainnet%2C+Pioneering+Decentralised+Web3+Infrastructure/25742646.html)

**Where Saito NFT content actually lives**
- "The UTXO set keeps the slips. It does not keep the message." The mint/transfer message is stored in `transaction.data`; the wallet entry holds only slips, id, `tx_sig`, optional ticker — "It is not the image, the file, or the module binary." Content is loaded by `SaitoNFT.fetchTransaction` from the local Archive by signature or by `field4` (= NFT id), else from the first connected peer. "Large content does not belong in the tuple"; the doc recommends "a reference when the payload is a file, a ROM, or a module." "A confirmed NFT with no Archive copy of its transaction will show in the wallet and fail to render." — [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- The browser NFT object copies `image`, `text`, `json`, `js`, `css`, `saito` fields straight from `tx.returnMessage().data`; base64 `data:` URIs are handled; no size limit is defined in that code — [saito-nft.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/saito-nft.js)
- The create UI stores `image`-type files as-is (no resize, no byte limit enforced); other types get a 512×512 thumbnail; the tx message is `{ data: obj, ticker, title, description }` — [create-overlay.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/overlays/create-overlay.js)
- "Archive data is application/service data, not consensus state." In Node, Archive uses SQLite; it "does not automatically remove a record because the underlying transaction later leaves the longest chain"; "Applications that need remote data must have a mechanism for obtaining it" — [SAITO-FRAMEWORK-STORAGE-ARCHIVE-REGISTRY-AND-PERSISTENCE.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-FRAMEWORK-STORAGE-ARCHIVE-REGISTRY-AND-PERSISTENCE.md)

**ATR mechanics ("rent or be pruned")**
- `G` = node's `genesis_period`; default 80,640 on non-test builds. ATR runs when `id > G + 1` and reads the block at height `id − (G+1)`. `atr_fee = tx_size * parent.avg_fee_per_byte` (size of the lookback transaction). `atr_payout = middle_amount * multiplier`, `multiplier = 1 + expected_atr_payout`, where `expected_atr_payout = parent.treasury / (G * parent.avg_nolan_rebroadcast_per_block)`. "If `atr_payout <= atr_fee`: do not create a transaction" (the amount is counted as fees instead). Total ATR payout per block is capped at 5% of treasury. Blocks at height `latest − 2G` are deleted. — [SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md](https://github.com/SaitoTech/saito/blob/master/README/consensus/SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md)
- For NFTs under ATR: "NFT groups of one lookback transaction are merged into one ATR transaction"; only the middle (deposit) slip "counts toward payout"; "Prepare output slips, only payload slip carries ATR amount"; if the payload cannot cover the fee the code logs "Payload slip didn't cover fee" and the value goes to fees — [block.rs (saito-rust-workspace)](https://github.com/SaitoTech/saito-rust-workspace/blob/master/saito-core/src/core/consensus/block.rs); [spec](https://github.com/SaitoTech/saito/blob/master/README/consensus/SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md)
- The deposit "is SAITO locked to the triple"; ATR "pays on that deposit rather than on the quantity"; a change that only replaces slips is classified as a `rebroadcast`; `expires_at` is "a local countdown and does not revoke anything" — [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Create-UI help text: "SAITO deposits circulate within assets and can be recovered by destroying the NFT." Deposit defaults to 1 SAITO per minted unit; mint cap 100,000,000 units; `fee` is hard-coded to 0 in the create overlay — [create-overlay.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/overlays/create-overlay.js)
- Older (2023) description: rebroadcast fee is "twice the average fee per byte paid by new transactions as determined over a smoothing period"; ATR txs carry the original transaction as embedded data; after two epochs "block producers will no longer require access to historical block data" but keep the 32-byte header hash — [saito-lite-rust docs/consensus/description.md](https://github.com/SaitoTech/saito-lite-rust/blob/master/docs/consensus/description.md). This conflicts with the 2026 spec's 1× `avg_fee_per_byte` formula; the 2026 spec is the implemented one.
- Epoch length/timing: `genesis_period` default 80,640 (template config, explorer default), `heartbeat_interval` default 30,000 ms (burnfee/routing-work target, not a hard block time); old blocks purged relative to `latest − 2*genesis_period`; slips valid only within the last `genesis_period` blocks — [about-scenario-config.md](https://github.com/SaitoTech/saito/blob/master/node/scripts/nettest/.agents/about-scenario-config.md). A dev config (`soptions`) uses 100,000 / 5,000 ms instead — [soptions](https://github.com/SaitoTech/saito/blob/master/node/config/soptions)
- Token persistence (UTXO stability across network resets) went live on mainnet in Sept 2023; issuance files are regenerated from the live UTXO hashmap at each hard fork and archived to GitHub — [Token Persistence Update, 2023-09-04](https://archive.saito.io/saito.tech/token-persistence-update-september-4-2023/)

**Other chains**
- Ethereum ERC-721: `tokenURI` is "A distinct Uniform Resource Identifier (URI) for a given asset"; the `image` field is "A URI pointing to a resource with mime type image/*"; the metadata extension is OPTIONAL — [EIP-721](https://eips.ethereum.org/EIPS/eip-721). Fully-on-chain variants use SSTORE2 (~200 gas/byte code-deposit, ~24 KB per file due to EIP-170) — [Art Blocks on-chain storage doc](https://abx.docs.artblocks.io/docs/protocol/onchain-storage)
- Solana Metaplex: standard NFTs point to off-chain storage (Arweave/Irys etc.) — [Metaplex storage providers](https://developers.metaplex.com/storage-providers); Metaplex Inscriptions put bytes in rent-exempt accounts at 0.003306 SOL overhead + 0.00000696 SOL/byte — [Metaplex Inscription FAQ](https://metaplex.com/docs/inscription/faq)
- Bitcoin Ordinals: content is "stored entirely on-chain, in the script of a taproot script-path spend", via commit + reveal, in `OP_FALSE OP_IF … OP_ENDIF` envelopes; gets the witness discount; each data push ≤ 520 bytes — [Ordinals docs](https://docs.ordinals.com/inscriptions.html)
- BSV 1Sat Ordinals: single-satoshi inscriptions; a pro-BSV source claims up to 50 MB in a single transaction and ~0.05 sat/byte fees (dated ~2023) — [CoinGeek](https://coingeek.com/ordinals-on-bitcoin-without-segwit-and-taproot/); [BSV Academy 1Sat](https://docs.bsvblockchain.org/bsv-academy/deep-dive-in-bsv-blockchain/the-power-of-tokens-and-smart-contracts/1sat-ordinals)
- Tezos FA2: "Because storage space on blockchains is expensive, developers don't put entire token metadata files on Tezos… put only the link to that data on Tezos itself" (IPFS via Pinata) — [docs.tezos.com NFT tutorial](https://docs.tezos.com/tutorials/create-an-nft/nft-tznft); TZIP-16 metadata JSON hosted on IPFS/GitHub/web — [ForkLog Tezos NFT guide](https://forklog.com/sp/dev-on-tezos/en/nft-issuance)
- Polkadot/Kusama: the `nfts` pallet on Asset Hub supports collection/item metadata, attributes (system/owner/user/external), atomic swaps, pre-signed mints, delegation; `Uniques` pallet deprecated — [Polkadot Wiki NFT pallets](https://wiki.polkadot.com/learn/learn-nft-pallets/); [pallet_nfts docs](https://paritytech.github.io/polkadot-sdk/master/pallet_nfts/index.html). Storage is deposit-based and refundable: "The deposit makes it explicit that there is a cost to storing information on-chain" — [Polkadot Forum](https://forum.polkadot.network/t/polkadot-assethub-high-nft-collection-deposit/4262)
- Arweave: one-time payment covers "the first 200 years of storage" assuming a 0.5%/yr storage-cost decline (historical decline >30%/yr); most of the payment goes into an endowment — [ArDrive](https://ardrive.io/articles/can-data-really-be-stored-forever/)

### Inferences
- Saito's model is best described as *state rent with a self-funding deposit*: each epoch, the NFT's own deposit earns a pro-rata share of the treasury (`deposit × expected_atr_payout`) and pays `tx_size × avg_fee_per_byte`. The NFT survives only while payout exceeds fee. Because the fee scales with *transaction size* and the payout with *deposit size*, a large inline payload with a tiny deposit will be pruned at the first epoch boundary, while a small tuple with a healthy deposit can persist indefinitely and even net-earn.
- "Fully on-chain" has a different meaning on Saito: bytes in the tuple's transaction are in blocks for at most ~2 epochs (then deleted), and are re-carried by ATR only while rent is covered; durable availability of the *media* depends on Archive nodes (application layer) that the project itself or peers run. This is closer to Filecoin/IPFS-with-incentives than to Ordinals.
- Data availability risk is therefore split: ownership (the tuple) is consensus-guaranteed while funded; content is service-guaranteed. A Saito NFT project must budget for running an Archive node (or paying one) in addition to deposits.

### Gaps
- Could not confirm whether the ATR rebroadcast transaction re-embeds the full original message bytes (2023 docs say ATR txs carry the original tx as embedded data; the 2026 spec computes `atr_fee` on the lookback tx size, which implies yes, but the spec's NFT section does not say explicitly).
- No protocol-level maximum transaction/message size was found for Saito; the only caps found are UI-level (20 outputs/tx, 100 total, 5 tx/block for atomize).
- The Saito whitepaper and 2021 ATR PDF could not be text-extracted; wiki.saito.io could not be read.

## Key Question 2 — Cost: approximate cost to mint and hold a 10 KB and a 1 MB fully on-chain NFT on each chain vs. Saito

### Takeaway
At today's prices, fully on-chain bytes cost roughly: BSV ≈ $0.0001 / $0.01 (10 KB / 1 MB), Arweave ≈ $0.0005 / $0.056 one-time, Bitcoin ≈ $2.4 / $217 at the 1 sat/vB floor (and 1 MB exceeds standard-relay limits), Tezos ≈ $0.75 / $77, Solana Inscriptions ≈ $8 / $800 (rent-exempt deposit), Ethereum L1 ≈ $15–$240 / $1,600–$24,500 depending on storage method and gas. ### Inferences
- In USD terms at today's prices Saito is almost certainly among the cheapest venues for *bytes* (token at $0.00036), but it is the only one where cost is *perpetual and market-indexed* (fee per byte re-priced each epoch) rather than one-shot; a SAITO price rise raises both deposits and rent in USD.
- Saito's "mint" cost is dominated by the refundable deposit rather than a burned fee (the create UI sets fee = 0), which is closer to Polkadot's refundable-deposit model and Nervos's locked-CKB model than to Ethereum gas.
- Because fee scales with tx size, the economically rational Saito design is small tuple + off-tuple media (Archive), which makes Saito's effective per-NFT rent tiny but shifts the real cost into infrastructure (Archive nodes).

### Gaps
- No public, current `avg_fee_per_byte` for Saito mainnet was obtainable (explorer page fetch returned empty; no third-party fee trackers). The team should read it from a running node (`block.avg_fee_per_byte`) or the explorer's supply view.

- Filecoin per-GB/yr pricing in 2025–26 was not found (only an undated forum note that Filecoin was "5–20x cheaper than S3" and briefly 1.79x costlier) — [Autonomi forum](https://forum.autonomi.community/t/market-research-on-market-size-and-growth/25885?page=3).

## Key Question 3 — Programmability: how NFT logic (royalties, transfers, auctions) is implemented on Saito without smart contracts, and what "application-layer modules" means for marketplaces and trust

### Takeaway
Saito has no VM; NFT logic is split between (1) a small set of consensus rules on Bound tuples, (2) a JSON-based pay-to-script-hash (P2SH) system that consensus evaluates only when a `0x00`-prefixed input is spent (CHECKSIG/CHECKMULTISIG/CHECKOWNNFT/CHECKPATHHOP/CHECKFIELD…), and (3) JavaScript modules (Store, Vault, Archive, Stack) that run on service nodes and in browsers and whose decisions "are not consensus rules." The live Store marketplace is a 1-of-2 multisig listing lock plus a buyer→(buyer+store) escrow with Store-signed fulfillment — atomic on-chain settlement, but the Store operator is trusted to fulfill and no royalty logic exists anywhere in the codebase.

### Cited Findings
- Transfer/split/merge are wallet-built Bound transactions: `createNFTTransaction` "does not mint" — it spends existing triples and creates new ones for the recipient, preserving the creator and splitting the deposit in proportion to quantity; `createSplitNFTTransaction` "spends one triple and creates two quantities that sum to it"; `createMergeNFTTransaction` combines triples of the same id; `createRemoveNFTTransaction` spends the triple out — [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md). Consensus side: "validation rules require all three slips to move together"; a "new NFT" is classified as exactly 1 Normal input and ≥3 outputs; Bound slips are excluded from fee accounting; "Non-ATR and Non-Bound Transaction has Bound UTXO" is rejected — [transaction.rs](https://github.com/SaitoTech/saito-rust-workspace/blob/master/saito-core/src/core/consensus/transaction.rs); [wallet.rs](https://github.com/SaitoTech/saito-rust-workspace/blob/master/saito-core/src/core/consensus/wallet.rs)
- P2SH: "A Saito script is a JSON object"; address = `0x00` + Blake3 hash of the canonical script (witness keys removed); when a tx spends a P2SH input, `Transaction::validate` runs the script and "A result other than `1` makes the transaction invalid." Opcodes: CHECKSIG, CHECKMULTISIG, CHECKOWNNFT, CHECKOWNNFTWHERE (adds creator/type checks), CHECKPATH/CHECKPATHHOP (delegation hops signed over `to|value|binding_hash`), CHECKFIELD, CHECKKEY, CHECKSENDER, CHECKRECIPIENT, IMPORTFIELD, SCRIPTHASH, AND/OR/NOT. "CHECKTIME therefore cannot succeed through the consensus spend path"; applications compare against `NOW` instead, and "NOW is deliberately not the transaction timestamp." "Consensus enforcement applies only to slips on `0x00` inputs. Application checks decide only what that application does." "An application that calls the WASM evaluator and then treats the result as success cannot change another node's view of the chain." — [SAITO-APPLICATIONS-PAY-TO-SCRIPT-HASH.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-PAY-TO-SCRIPT-HASH.md)
- Store marketplace flow: seller's `list-asset` sends the triple to a P2SH listing address built from seller + Store keys (1-of-2 CHECKMULTISIG — "The listing lock is P2SH"); buyer's `purchase-asset` pays into a P2SH escrow (buyer + Store keys) with `nft_id, quantity, price, fee, refund`; Store node checks `unit_price × quantity + fee` and listing status, else refunds; `createFulfillmentTransaction` spends escrow + listing triples in one Bound tx, paying buyer the NFT and pro-rata deposit, re-listing remainder, paying sellers `unit_price × take_qty`; witnesses bind to all outputs (Blake3 over serialized outputs). Delist is seller-only. Rentals (`store-nft-rental`, 1–24 h) add a `delegated` hop. No fee output and no royalty logic appear in fulfillment; `this.fee = 0` in the module; browser nodes skip order processing — [store/lib/transactions.js](https://github.com/SaitoTech/saito/blob/master/node/mods/store/lib/transactions.js); [store.js](https://github.com/SaitoTech/saito/blob/master/node/mods/store/store.js). Listings are confirmed on-chain then indexed in the Store node's `warehouse.db`; "Listing moderation: node admins, plus anyone on the Store seller whitelist"; "An empty list authorizes nobody" — [store.js](https://github.com/SaitoTech/saito/blob/master/node/mods/store/store.js)
- A GitHub code search for "royalt" across `SaitoTech/saito` returned only unrelated license text and a card name — no royalty implementation exists (gh CLI search, 2026-10-10).
- Vault = "Storage Vault regulated by NFT Keys": access keys are NFTs (`vault-nft-key`, `vault-nft-rental`); the default access script is CHECKOWNNFT over the three UTXO keys; the server recomputes the script hash and evaluates it before loading from Archive; rentals use a loan script that "allows the renter before `expires_at` and the creator after it, judged by the evaluating node's clock"; "Two Vault nodes can disagree around an expiry"; "The file is not on-chain" and an operator who ignores the script "can still read the Archive row on that machine" — [vault.js](https://github.com/SaitoTech/saito/blob/master/node/mods/vault/vault.js); [P2SH doc](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-PAY-TO-SCRIPT-HASH.md)
- Executable NFTs: create types include `image, token, text, css, json, js, saito-app`; NFT Studio is a "browser-based code editor" to "Create, preview, and publish JavaScript and CSS NFTs" (beta) — [create-overlay.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/overlays/create-overlay.js); [nftstudio.js](https://github.com/SaitoTech/saito/blob/master/node/mods/nftstudio/nftstudio.js). Enabling an app NFT "is a local decision. It is not a transfer and it is not consensus"; the card records `nft.tx_sig` in `app.options.permissions.nfts` and calls `installLocalApplication`; "There is no consensus 'install module' transaction"; "Transferring the NFT does not uninstall the previous holder's copy" — [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- The repo ships an `nft-security-audit` skill because executable NFTs may run "in the application's main window, an iframe, a worker, a server runtime, or a privileged extension"; "A worker or iframe alone does not establish isolation"; it flags reachable `app.wallet`, `returnPrivateKey`, signing hooks, exfiltration via fetch/WebSocket/postMessage, and persistence via storage/service workers — [nft-security-audit SKILL.md](https://github.com/SaitoTech/saito/blob/master/.agents/skills/nft-security-audit/SKILL.md)
- Contrast — Ethereum: EIP-2981 only signals royalty info; "ERC 2981… does not 'enforce' the royalties"; wrappers and plain ERC-721 transfers bypass it; OpenSea made royalties optional (0.5% min) for collections without on-chain enforcement — [OpenZeppelin forum](https://forum.openzeppelin.com/t/erc-2981-and-royalties-in-general/31953); [The Block](https://www.theblock.co/post/178603/why-nft-royalties-are-almost-impossible-to-enforce-on-chain); [Decrypt](https://decrypt.co/116768/opensea-chang)
- Contrast — Polkadot `nfts` pallet has built-in atomic swaps, a built-in marketplace, pre-signed mints, attribute approvals, and "Smart attributes allowing external entities to update NFT properties" — [Polkadot Wiki](https://wiki.polkadot.com/learn/learn-nft-pallets/)
- Earlier roadmap language: Saito supports "third-party 'cryptocurrency modules' that provide a bridge to other networks"; default bundles for Polkadot, Kusama and other Substrate networks — [saito-crypto-api-modules](https://github.com/SaitoTech/saito-crypto-api-modules)

### Inferences
- Saito's programmability for NFTs is *ownership-verification-centric* (prove you hold a tuple; lock a tuple behind a multisig or NFT-ownership script), not *state-machine-centric*. Anything that needs enforced per-transfer side effects — creator royalties, auction settlement with bids, bonding curves, on-chain randomness — must be done by a service module that users trust, or by designing the sale to flow through a P2SH escrow so settlement is atomic.
- Royalties on Saito are structurally in the same position as on Ethereum after 2023 (marketplace-enforced, not protocol-enforced), except Saito has even fewer hooks: the Store is the only marketplace and it currently pays sellers 100%.
- "Application-layer modules" means the marketplace operator is a semi-trusted counterparty: it cannot steal a listed NFT alone (1-of-2 with the seller) and cannot change the sale outputs without invalidating witnesses, but it *can* fail to fulfill, and the code shows no timeout path returning escrowed funds. A serious NFT project would want a timelocked refund — which is blocked today because CHECKTIME "cannot succeed through the consensus spend path."
- Executable (JS/CSS/app) NFTs are a genuine differentiator but are closer to "signed, transferable app bundles" than enforced licenses; uniqueness of *ownership* is on-chain, uniqueness of *execution* is not.

### Gaps
- The Saito security/trust-model doc and the game-engine doc are placeholders ("not yet fleshed out") — [SAITO-AI-DEVELOPMENT-SAITO-SECURITY-AND-TRUST-MODEL.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-AI-DEVELOPMENT-SAITO-SECURITY-AND-TRUST-MODEL.md); [SAITO-APPLICATIONS-GAMES-AND-THE-SAITO-GAME-ENGINE.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-GAMES-AND-THE-SAITO-GAME-ENGINE.md).
- Who may trigger Store fulfillment and how the Store key's witness is authorized lives in `store/lib/scripting.js`, which was not read.
- No auction, offer, or bidding module was found in the `node/mods` listing.

## Key Question 4 — Interoperability: can Saito NFTs be bridged (Mixin, wrapped tokens, ERC-20 SAITO)? Any cross-chain NFT standards relevant to Saito?

### Takeaway
There is no NFT bridge for Saito. The "Mixin" module is a custodial multi-asset deposit/withdrawal rail (BTC, ETH, SOL, TRX, USDT, USDC, XMR, ZEC, NEAR, BNB, etc.) that lets Saito apps and the Store accept other cryptocurrencies via Mixin's API — it has nothing to do with NFTs or with moving SAITO. The SAITO token exists as ERC-20 and BEP-20 wrappers with a one-way migration to mainnet; wrapped tokens remain valid. No cross-chain NFT standard (e.g., wrapped Saito tuples on EVM) was found.

### Inferences
- A Saito NFT's identity (slip3 key = block/tx/slip-derived UUID + 16-byte type) is unique and verifiable with SPV-style proofs, so a *custodial* wrap (lock tuple at a P2SH multisig, mint ERC-721 pointer) is feasible with existing primitives; a trust-minimized bridge is not, because Saito has no light-client verification on EVM and no EVM-side verifier of Saito blocks was found.

## Key Question 5 — Unique angles: in-browser full-node-like apps, P2P game state, NFT-gated gameplay, NFTs as access/identity, expiring or rent-paying NFTs, NFTs that earn fees — and whether the team/community has proposed them

### Takeaway
Most of the "novel" use cases are not hypothetical on Saito — several are already implemented at the application layer: NFT-keyed encrypted storage (Vault), hourly NFT rentals with delegation hops (Store + Vault + N-WASM ROM rentals), executable JS/CSS/app NFTs (NFT Studio, `saito-app` type), NFT-gated private posts (Stack), fractional/"atomized" NFTs, and an MTG-style NFT card game (Realms) in development. Rent-paying and yield-earning NFTs are not a feature but an unavoidable property of ATR: every NFT deposit earns the ATR payout and pays per-byte rent each epoch. Protocol-level "expiry" is emergent (deposit too small → pruned), not declarative.

### Cited Findings
- Browser as node: "start a Saito node in this browser, and inspect the peers carrying traffic across the network"; "Saito modules are browser-native applications with access to shared network, wallet, identity"; Arcade: "Meet players and launch peer-to-peer games with verifiable rules"; RedSquare: "Post, follow and discover without a platform owning the conversation" — [saito.io](https://saito.io/)
- P2P game state: "players broadcast moves to each other and execute them in parallel"; cryptographic techniques such as mental poker "ensure provably-fair deck shuffling, dice rolls and other core game functions" — [W3F grant application](https://github.com/w3f/Grants-Program/blob/master/applications/saito-game-protocol-and-engine.md). Conquest module README: "Battles use an attacker commitment, fresh signed defender entropy, and an attacker reveal"; "a disconnected participant can stall the exchange; there is no automatic timeout adjudication" — [conquest README](https://github.com/SaitoTech/saito/blob/master/node/mods/conquest/README.md)
- NFT card game: "our Magic The Gathering-style NFT card game removes more roadblocks"; "much of the artwork has been completed, the team is looking for those willing to take some initiative" — [Saito Summer 12 (2024-11-04)](https://archive.saito.io/saito.tech/saito-summer-12-the-big-picture/); a `realms` module exists in `node/mods` — [GitHub API listing](https://api.github.com/repos/SaitoTech/saito/contents/node/mods)
- NFT-gated storage/identity: Vault access keys are NFTs; "Stack's private posts use a similar type-and-creator check"; CHECKOWNNFTWHERE adds creator and type checks — [P2SH doc](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-PAY-TO-SCRIPT-HASH.md); [vault.js](https://github.com/SaitoTech/saito/blob/master/node/mods/vault/vault.js)
- Rentals: Store `rent` listing mode, duration clamped 1–24 hours, rights default `all`; rental NFTs are type `store-nft-rental` — [store.js](https://github.com/SaitoTech/saito/blob/master/node/mods/store/store.js). "N-WASM's rental timer does not spend the NFT and it does not change Archive `owner` by itself" (N-WASM = NES emulator module with ROMs) — [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md); [nwasm roms in repo (gh search)](https://github.com/SaitoTech/saito/tree/master/node/mods/nwasm)
- Executable NFTs and permissions: `saito-app` type; `SaitoNFTCard` toggles enable/disable; `app.options.permissions.nfts` allowlist; `can_toggle` when the NFT has css/js or is `saito-app` — [saito-nft-card.template.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/saito-nft-card.template.js); [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md). `rustscript` module has a "publish-nft" overlay (gh search).
- Fractionalization: "Your browser is currently atomizing this NFT into 1-unit chunks" (NFTAtomize overlay; caps of 20 outputs/tx, 100 total, 5 tx/block are UI-only) — [nft-atomize.template.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/overlays/nft-atomize.template.js); tokens: an optional ticker forces type `token` — [create-overlay.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/overlays/create-overlay.js)
- Rent-paying / fee-earning: ATR payout on the deposit = `middle_amount × (1 + treasury/(G × avg_nolan_rebroadcast_per_block))`, capped at 5% of treasury per block; treasury is fed when a block has no golden ticket ("The treasury contribution is not paid to a key") — [consensus spec](https://github.com/SaitoTech/saito/blob/master/README/consensus/SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md). Wallet comment: slip2 is where the holder is "rebroadcasting fees and receiving any ATR payout" — [wallet.rs](https://github.com/SaitoTech/saito-rust-workspace/blob/master/saito-core/src/core/consensus/wallet.rs). Third-party summaries describe ATR as distributing "25% of on-chain network fees to holders of unspent UTXOs" — [MEXC](https://www.mexc.com/news/279876) (not confirmed in the spec; treat as unverified).
- Routing economics: fees are split between a golden-ticket miner and a router chosen by lottery weighted by routing work; the fee is "halved by each additional hop beyond the first"; example split 57%/29%/14% — [saito-lite-rust description.md](https://github.com/SaitoTech/saito-lite-rust/blob/master/docs/consensus/description.md). Mainnet PR: Saito "compensates nodes for routing, storage, and compute work" — [StreetInsider](https://www.streetinsider.com/Globe+Newswire/Saito+Blockchain+Launches+Mainnet%2C+Pioneering+Decentralised+Web3+Infrastructure/25742646.html)
- Expiry: `expires_at` "is a local countdown and does not revoke anything"; loan scripts are "judged by the evaluating node's clock" — [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md); [P2SH doc](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-PAY-TO-SCRIPT-HASH.md)
- Archive nodes and data ownership: "Archive Nodes support decentralized data ownership and access of data in an environment of primarily P2P-connected clients"; "users can encrypt their data for a more secure experience than services like Google Drive"; "ATR Hyperloop" with a "significantly shortened" ATR epoch was being considered internally — [Saito Summer 12](https://archive.saito.io/saito.tech/saito-summer-12-the-big-picture/)

### Inferences
- **Game assets in Arcade**: the tuple model fits inventory-style assets (quantity in slip1, split/merge, atomize) and the P2SH CHECKOWNNFT/CHECKOWNNFTWHERE opcodes give "prove you hold a card of type X from creator Y" at zero gas. But because game moves are off-chain P2P and there is no on-chain state machine, "NFT-gated gameplay" is enforced by peers refusing to play with you, not by consensus — adequate for turn-based games with a referee-less honest-majority assumption, not for high-stakes competitive play.
- **Social collectibles in Red Square/Stack**: NFT-gated private posts and NFT-keyed vaults already exist; identity is the keypair, so "NFT as access/identity" is the native pattern, not a bolt-on.
- **Living / self-funding NFTs**: a design that sets deposit D such that `D × expected_atr_payout > tuple_size × avg_fee_per_byte` yields an NFT that is net-positive every epoch while it sits unspent — a genuinely novel primitive ("the NFT pays its own rent and accrues yield"). Conversely a low-deposit NFT with a large inline payload is an "expiring" NFT whose lifetime is one epoch. Expiry timing is probabilistic (depends on treasury and aggregate rebroadcast volume), so it is a *mechanism*, not a product feature yet.
- **Executable NFTs as distributable apps/mods**: the `saito-app`/JS/CSS types plus NFT Studio make "sell a game mod, theme, or ROM as an NFT" the clearest Saito-native product; the audit skill shows the team knows this is also the biggest attack surface.
- Nothing found suggests the team has proposed NFTs that *earn routing fees* specifically (routing rewards go to nodes that relay transactions, not to UTXO holders); the fee-earning angle that exists is the ATR deposit yield.

### Gaps
- No team or community document explicitly proposes "expiring NFTs," "self-funding NFTs," or "NFTs that earn ATR yield" as product features; these are inferences from the consensus formulas.
- Realms (NFT card game) status in 2026 unknown beyond the module directory existing.
- Whether Red Square (vs. the newer Stack module) has shipped NFT-gated features was not confirmed.

## Key Question 6 — Anti-patterns: which NFT use cases are a bad fit for Saito

### Takeaway
Saito is a poor fit for permanent, fire-and-forget art archival; for anything needing protocol-enforced royalties or complex auction/DeFi composability; for high-frequency trading; and for large inline media. These follow directly from ATR rent, the absence of a VM, 30-second-heartbeat block economics, and the per-byte recurring fee.

### Cited Findings
- Rent and pruning: "If `atr_payout <= atr_fee`: do not create a transaction"; blocks deleted at `latest − 2G` — [consensus spec](https://github.com/SaitoTech/saito/blob/master/README/consensus/SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md). "Large content does not belong in the tuple." — [NFTS-AND-SCRIPTING.md](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-NFTS-AND-SCRIPTING.md)
- Content availability is not consensus: "Archive data is application/service data, not consensus state" — [Storage doc](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-FRAMEWORK-STORAGE-ARCHIVE-REGISTRY-AND-PERSISTENCE.md)
- No timelocks in consensus path: "CHECKTIME therefore cannot succeed through the consensus spend path" — [P2SH doc](https://github.com/SaitoTech/saito/blob/master/README/coding/SAITO-APPLICATIONS-PAY-TO-SCRIPT-HASH.md)
- No royalties in code (gh code search, 2026-10-10); Store pays sellers `unit_price × take_qty` with no fee output — [store/lib/transactions.js](https://github.com/SaitoTech/saito/blob/master/node/mods/store/lib/transactions.js)
- Block timing: `heartbeat_interval` default 30,000 ms governs burnfee/required routing work; production is off by default (`disable_block_production: true`) — [consensus spec](https://github.com/SaitoTech/saito/blob/master/README/consensus/SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md); [about-scenario-config.md](https://github.com/SaitoTech/saito/blob/master/node/scripts/nettest/.agents/about-scenario-config.md)
- Executable-NFT risk surface: drainers can "abuse signing without extracting a key"; persistence via service workers/timers can survive reloads — [nft-security-audit SKILL.md](https://github.com/SaitoTech/saito/blob/master/.agents/skills/nft-security-audit/SKILL.md)
- Code maturity signals: the create overlay's minimum-deposit check effectively enforces 1 nolan rather than 1 SAITO; `getTotalAmount()` uses `parseInt` on BigInts; `createBoundTransaction` accepts an `nft_data` parameter it never uses; "TEMP: prove store-nft-rental arrives self-contained" debug code — [create-overlay.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/overlays/create-overlay.js); [saito-nft.js](https://github.com/SaitoTech/saito/blob/master/node/lib/saito/ui/saito-nft/saito-nft.js); [wallet.rs](https://github.com/SaitoTech/saito-rust-workspace/blob/master/saito-core/src/core/consensus/wallet.rs); [store.js](https://github.com/SaitoTech/saito/blob/master/node/mods/store/store.js)
- Market context: SAITO ≈ $0.00036 with an ~80% one-year decline per Coinbase — [Coinbase](https://www.coinbase.com/price/saito); "a niche Layer-1 project" — [OneKey](https://onekey.so/blog/ecosystem/best-saito-wallets-in-2025)

### Inferences
- **Permanent art archival without ongoing fees**: wrong chain. Use Arweave (one-time endowment) or Ordinals/BSV; on Saito an abandoned collection with insufficient deposits is pruned within an epoch or two, and even a funded tuple's media depends on someone running Archive.
- **Protocol-enforced royalties / creator fees**: not possible; even marketplace-enforced royalties need Store changes.
- **DeFi composability (NFT lending pools, AMMs, fractional vaults with pricing logic)**: no VM, no CHECKTIME, no on-chain state beyond UTXOs; only simple escrow/multisig/ownership predicates.
- **High-frequency trading or bidding wars**: 30 s heartbeat economics, routing-work requirements, and a single Store operator fulfilling orders make this impractical.
- **Large inline media (video, hi-res art)**: the per-epoch fee scales linearly with tx bytes forever; the docs themselves steer you to references.
- **Trust-minimized marketplaces**: today's Store requires trusting the operator to fulfill; without consensus timelocks, escrow timeouts cannot be enforced on-chain.
- **Untrusted executable NFTs for a broad consumer audience**: without a documented sandbox, JS NFTs are a wallet-drainer vector; a project should either avoid JS-type NFTs or ship its own strict iframe/CSP sandbox.

### Gaps
- No empirical data on Saito mainnet throughput, confirmation latency, or Store order volume was found.
- No incident reports or audits of the Store/Vault modules were found (the security-trust doc is a placeholder).

## Key Question 7 — Lessons from comparable "data chains" (Arweave, Filecoin, BSV, Koinos, Nervos) on persistent-asset economics that would inform a Saito NFT project

### Takeaway
Nervos CKB is the closest economic cousin (state rent paid via dilution on locked CKB = storage right; NervosDAO hedges it), and its lesson is that rent-based models need a visible "yield vs. dilution" dashboard for holders. Arweave shows the opposite pole (one-time endowment, pricing on a 200-year horizon) and highlights that Saito's recurring rent is actually a more honest price signal but a worse UX. BSV demonstrates that cheap permanent bytes do not by themselves create NFT demand. Ethereum's own state-rent debates (deposit-based rent) show Saito has shipped what Ethereum researchers only proposed.

### Cited Findings
- Nervos: "Ownership of CKByte grants the holder to one byte of data storage"; CKBytes "remain locked for the Cell's duration"; "State Rent continuously compensate miners for data preservation"; the inflation funding state rent "comes from a process known as Secondary Issuance"; holders not occupying space "may gain interest from Secondary Issuance by locking their CKBytes in Nervos DAO" — [Nervos docs: economics](https://docs.nervos.org/docs/concepts/economics); fixed secondary issuance 1.344 B CKB/yr split among miners, NervosDAO depositors, treasury — [ViaBTC](https://www.viabtc.com/blog/334?category=0). "All assets on Nervos require data storage and are therefore subject to state rent" — [Nervos token-standards economics](https://docs.nervos.org/docs/assets-token-standards/economics)
- Arweave: one-time fee covers 200 years assuming 0.5%/yr cost decline vs >30.5%/yr historical; "a small portion" goes to storers upfront, "the rest… into an endowment" — [ArDrive](https://ardrive.io/articles/can-data-really-be-stored-forever/); sources disagree on the split (5%/95% vs 15%/85%) — [Permaweb Journal storage endowment](https://permaweb-journal.ar.io/article/storage-endowment-explained.html); live 0.01359 AR/MiB — [arweave.net/price](https://arweave.net/price/1048576)
- Koinos: Mana is "a property of KOIN, not a separate token"; "regenerates at 20% of your total Mana per day"; "Another party, such as a dApp, can pay your transactions with its Mana"; no storage-specific pricing on the mana page — [Koinos docs: Mana](https://docs.koinos.io/overview/mana/)
- BSV: ~0.05 sat/byte and up to 50 MB per tx (promotional, dated) — [CoinGeek](https://coingeek.com/ordinals-on-bitcoin-without-segwit-and-taproot/); 1Sat is "more cost-effective than other protocols because it operates at the single-satoshi level" — [BSV Academy](https://docs.bsvblockchain.org/bsv-academy/deep-dive-in-bsv-blockchain/the-power-of-tokens-and-smart-contracts/1sat-ordinals)
- Bitcoin: fees sat at the 1 sat/vB floor for weeks in spring 2026 and the BRC-20 market "shrunk sharply since its peak" — [btc.network](https://btc.network/nl/blog/bitcoin-network-weekly-report-april-6-12-2026); [spark.money](https://www.spark.money/research/bitcoin-ordinals-brc20-evolution)
- Ethereum state-rent research proposed "paying rent with deposits" (never adopted) — [ethresear.ch](https://ethresear.ch/t/paying-rent-with-deposits/2221/20)
- Polkadot: "NFT deposits were 'chosen somewhat arbitrarily at genesis'" and there is "no way to calculate the 'real cost of storage'"; artists worried a $40 collection deposit "rises with the DOT price" — [Polkadot Forum](https://forum.polkadot.network/t/polkadot-assethub-high-nft-collection-deposit/4262)
- Saito's rent is market-indexed each epoch (`avg_fee_per_byte`) and yield is treasury-indexed (`expected_atr_payout`) — [consensus spec](https://github.com/SaitoTech/saito/blob/master/README/consensus/SAITO-CONSENSUS-MECHANISM-DESCRIPTION.md)

### Inferences
- *Lesson from Nervos*: treat the NFT deposit as the product's "storage bond"; publish a holder-facing calculator (deposit, bytes, current `avg_fee_per_byte`, `expected_atr_payout`) and auto-top-up tooling, otherwise users will discover pruning the hard way. Saito lacks a NervosDAO-style hedge, but a project could offer one at the app layer (e.g., a treasury that tops up member NFTs).
- *Lesson from Arweave*: if the project needs guaranteed media permanence, store media on Arweave (≈$0.056/MB) and keep only the Arweave ID in the Saito tuple — the tuple then costs a few hundred bytes of rent per epoch, and ownership/logic stay on Saito. This hybrid mirrors Metaplex's architecture.
- *Lesson from Polkadot*: refundable deposits denominated in a volatile token create UX anger when price rises; because Saito's deposit is also the yield base, price appreciation at least pays the holder, but mint UX should quote deposits in USD-equivalent.
- *Lesson from BSV/Ordinals*: ultra-cheap bytes commoditize "on-chain-ness"; Saito's defensible angle is not cheap bytes but ownership-gated P2P applications (Vault, rentals, executable NFTs), so a project should lead with utility, not storage.
- *Lesson from Koinos*: regenerating resource credits let dApps sponsor user activity; Saito's `fee = 0` mint path and "unfunded carrier" purchase txs suggest sponsorship patterns are possible but undocumented — worth prototyping for onboarding.

### Gaps
- No academic paper directly comparing rent-based vs endowment-based NFT persistence was found in this pass; the comparison above is assembled from protocol docs.
- Filecoin NFT-storage economics (NFT.Storage transition to paid tiers, deal renewal costs) were not researched in depth here.
- Sui's storage-fund model appeared in search results ([Sui storage fees](https://www.sui.io/blog/storage-fees-explained.md)) but was not read; it is another rebate-based comparator worth a follow-up.
